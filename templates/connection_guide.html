{% if vendor == 'unifi' %}
  1. En UniFi Site Manager ↗, entra en los ajustes y busca API Keys. Crea una clave para este servicio con acceso al cliente.
  2. En la ficha del equipo del SOC, pulsa Configurar API de UniFi Cloud. Pega la clave en Clave API y pulsa Validar y guardar clave.
  3. Pulsa Buscar sedes y comprobar acceso, elige la consola del cliente por su nombre y modelo y pulsa Vincular y comprobar exportación.

Si tu clave ve varias consolas, confirma la correcta antes de vincularla. «API verificada» confirma el acceso a Cloud; aún falta validar los logs.

{% elif vendor == 'opnsense' and method == 'api' %}
  1. En OPNsense, abre Sistema → Acceso → Usuarios. Crea o edita una cuenta dedicada al SOC y asígnale permisos para consultar el estado y firmware, consultar/modificar destinos syslog y aplicar el servicio. Los nombres de los permisos pueden variar por versión.
  2. En las claves API del usuario, pulsa +. Se descarga un archivo que contiene key=... y secret=....
  3. En el SOC, pulsa Configurar API de OPNsense. Escribe la dirección HTTPS completa, con el puerto si no es 443. Copia solo el valor tras key= en Clave API y solo el valor tras secret= en Secreto API. Ambos están en el mismo archivo descargado.
  4. Si el certificado usa una CA privada, pega el certificado público de esa CA en formato PEM. El certificado HTTPS debe estar vigente y contener el nombre o la IP de la dirección usada.
  5. Pulsa Guardar y configurar exportación. Si ya has guardado las credenciales, usa Probar y reconfigurar exportación.
No encuentro el secreto o falla el certificado

El secreto está en la línea secret= del archivo descargado junto a la clave. Si has perdido el archivo, genera una nueva pareja y sustituye ambos valores en el SOC.

Pegar la CA resuelve la confianza, pero no corrige un certificado caducado ni un nombre/IP incorrecto. Revisa el certificado del WebGUI en OPNsense o usa su nombre válido. Para una alternativa disponible en el portal, consulta la guía de SSH.

{% elif vendor == 'opnsense' and method == 'ssh' %}
  1. En OPNsense, habilita SSH en Sistema → Ajustes → Administración y permite el acceso desde la VM SOC al puerto elegido.
  2. Prepara una cuenta dedicada con una shell válida, como /bin/sh o /bin/csh, acceso SSH y permiso para administrar syslog mediante sudo. El acceso con contraseña debe estar habilitado para usar el formulario actual del portal.
  3. En el SOC, pulsa Configurar SSH, indica dirección, puerto y usuario, y pulsa Obtener huella SSH.
  4. Comprueba la huella con la mostrada por el firewall o facilitada por su administrador. Repítela en el campo de confirmación, introduce la contraseña y pulsa Guardar y configurar exportación.

La contraseña se introduce después de obtener la huella. El portal la guarda cifrada y la usa también para sudo si el equipo la solicita.

¿Incluye los ataques de CyberSecure?

Wazuh puede analizar las detecciones de seguridad que UniFi exporta por Activity Logging. La tabla de Traffic Flows no equivale a esos eventos; no debe presentarse como una copia completa en Wazuh.

También usamos Zenarmor, Suricata o ClamAV

El syslog general de OPNsense no confirma que estén llegando las alertas de cada complemento. Cada fuente requiere comprobar su exportación y que Wazuh interpreta un evento real.

Zenarmor: en Settings → Reporting & Data → Streaming Data, activa la exportación Syslog hacia el mismo destino UDP y selecciona Alerts. Esta función requiere SOHO o Business; Free y Home no la incluyen. En Zenarmor 2.5 y posteriores, los informes locales usan SQLite o Elasticsearch 8, no MongoDB.

Suricata y ClamAV: el administrador SOC debe comprobar los registros disponibles en esa instalación y preparar su recogida y reglas. Esta guía no da estos conectores por configurados al guardar la API de OPNsense.

Si algo no funciona

No veo dónde poner la contraseña SSH

En Configurar SSH, introduce dirección, puerto y usuario y pulsa Obtener huella SSH. Después aparece «Confirmar huella y guardar», con el campo de contraseña. En OPNsense, comprueba que el usuario tenga shell válida, acceso SSH y permiso sudo para configurar syslog.

API verificada, pero no hay eventos

Revisa el destino, UDP {{ syslog_port }}, la ruta de salida y los filtros intermedios. Si hay NAT, comprueba el reenvío y el origen real observado. La conexión API y el envío de logs son conexiones distintas. Repite la verificación de exportación y revisa si Wazuh está preparado para ese origen.

Conectado, configurado y receptor preparado: ¿qué significa?

Acceso verificado: el portal puede consultar el equipo. Exportación configurada: el destino se ha guardado o comprobado. Receptor preparado: Wazuh admite el origen registrado. El alta queda validada cuando un evento real llega, se interpreta y se atribuye al cliente.

Veo ataques en el firewall, pero no en Wazuh

Comprueba que el tipo de detección se exporte y que exista una regla que interprete ese formato. En UniFi, Traffic Flows y Activity Logging pueden tener contenidos distintos. En OPNsense, los complementos requieren su propia validación. Un panel vacío no confirma ausencia de ataques.

No tengo permiso para gestionar conexiones

Pide al administrador del portal el permiso «Gestionar conexiones» (core.manage_connections). Podrás introducir credenciales en los formularios específicos; no las guardes en notas ni en la lista de esta guía.
